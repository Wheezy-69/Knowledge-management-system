# Backup, export, and restore

## 1. What the feature does

Download a portable backup containing vaults, sections, problems, attempts, tags,
assignments, related links, blocks, and cover images. Restore creates new copies
with new record IDs and attachment filenames. It never clears or replaces the
existing workspace. Reimporting the same file creates another set of copies.

## 2. Implementing files

- `app/Services/KnowledgeBackup.php`: snapshot, validation, and restoration.
- `app/Http/Controllers/BackupController.php`: web download/upload endpoints.
- `resources/js/pages/backups/Index.vue`: export and confirmed import UI.
- `routes/console.php`: `php artisan vault:backup`.
- `tests/Feature/KnowledgeExpansionTest.php`: integrity and failure coverage.

## 3. Frontend communication

Download backup uses a normal link to the generated export URL because its
response is a file, not an Inertia page. Restore posts a File and a confirmation
checkbox using Inertia. Validation errors appear on the backup/confirmation
fields. Upload progress and a processing label are shown.

The CLI command writes a new uniquely named file in the private disk's
`backups/` directory, reads it back, validates it, then prints its path.
The real pre-expansion backup was created there before the additive migration.
Backup files are ignored by Git and were not committed or uploaded.

## 4. Controller, model, and database

Export reads a consistent database transaction snapshot and embeds raster covers.
It refuses to report success if a referenced cover is missing. Import validates
the complete document before beginning database writes. A transaction inserts
fresh records and remaps foreign IDs. If a write fails, it rolls back database
changes and removes only attachment paths generated by that import.

Tag keys matching an existing catalog tag reuse its identity. Original imported
JSON labels are preserved; pivots are rebuilt through ProblemTags for compatibility
with pre-normalization backups. Existing records are not modified.

### Portable format version 1

The JSON root contains:

| Key        | Meaning                                 |
| ---------- | --------------------------------------- |
| format     | The string knowledge-vault              |
| version    | Integer 1                               |
| created_at | Export timestamp                        |
| counts     | Expected row counts for each data array |
| sha256     | SHA-256 of the canonical data object    |
| data       | Eight named arrays described below      |

Data arrays are `vaults`, `sections`, `problems`, `attempts`, `tags`,
`problem_tag`, `problem_links`, and `content_blocks`. Rows carry exported IDs,
foreign IDs, and stored fields. Timestamp fields are preserved. A problem's
`tags` is an array or null in the archive, rather than an encoded JSON string.

Vault rows replace the internal cover_path with `cover: null` or
`cover: { sha256, data }`, where data is base64-encoded image bytes. Imported
paths are generated afresh; an archive cannot choose a disk destination.

Canonical checksum encoding is PHP JSON encoding of data with
JSON_UNESCAPED_UNICODE and JSON_UNESCAPED_SLASHES. Property/array order matters.
The checksum detects corruption; it is not a signature or proof of provenance.
A third party could modify a backup and recompute its checksum, so schema and
content validation are still essential.

Before expansion tables existed, the same format represented those tables as
empty arrays. Such an archive can be restored after running the expansion
migration; legacy problem JSON tags recreate assignments.

## 5. Validation and errors

The archive is limited to 20 MB and each array to 10,000 rows. PHP's configured
upload/post limits may impose a lower effective limit. Use a database-plus-private-
cover-directory backup for larger workspaces.

Validation checks format/version, checksum, counts, field types/lengths, distinct
IDs, parent references, order numbers, duplicate links/assignments, self-links,
normalized tag keys, agreement between JSON tag labels and normalized assignments,
and duplicate legacy sources. Pre-normalization archives with empty tag tables
rebuild assignments from their JSON labels. Each embedded image must
decode, match its checksum, be at most 2 MB, and be JPEG/PNG/GIF/WebP.

A missing image, invalid file, or storage failure prevents a successful restore.
The confirmation checkbox is required. Files are private and unencrypted, so
store them appropriately. No users, credentials, sessions, environment variables,
or API keys are exported.

## 6. Testing

KnowledgeExpansionTest exercises Unicode, exact source whitespace, tag assignments,
attempts, blocks, reciprocal links, attachment bytes, importing without overwriting,
malformed JSON, unsupported format, altered checksums, missing parents, missing
covers, missing confirmation, inconsistent tag assignments even with a recomputed
checksum, and storage failure rollback/cleanup.

Run `php artisan test --filter=KnowledgeExpansion`. Tests use an in-memory
database and fake storage, not the real backup or local records.

## 7. Implementation decisions

A single JSON file avoids a ZIP dependency and archive-path extraction risks.
Base64 adds size overhead, which is why this portable format has a documented
limit. Append-only restore is deliberate: there is no destructive restore mode,
ID overwrite, automatic deduplication of knowledge, or synchronization tool.

The database and file operations are coordinated by cleanup but are not one
physical transaction. A process crash during import can leave an orphan file,
even though normal caught failures clean up. Back up the SQLite file and private
cover directory separately for disaster recovery.

## 8. Rebuild independently

1. Define the format, version, fields, and ID relationships explicitly.
2. Write export and validate the resulting document before adding restore.
3. Verify every parent exists within the archive.
4. Generate new IDs and filenames; never trust incoming filesystem paths.
5. Restore parents before children inside a transaction.
6. Track newly written attachments for failure cleanup.
7. Test a round trip and deliberate corruption before exposing the upload UI.
